A running log of what I am building, mostly the Attention Accelerator right now — the honest version, with the bugs and the lessons, newest entries at the top.

2026-08-02M5 · in progress

Dropping into RTL: a dot-product MAC in SystemVerilog

This is the milestone the whole project was pointing at. I am now building the attention core in synthesizable SystemVerilog, targeting a Xilinx FPGA through Vivado. The build order inside M5 is qkt → row-max → softmax → PV → full naive core, and I started at the very bottom: the dot-product MAC that lives inside QK⊤.

The unit, dot4, computes sum(a[k]*b[k]) for two length-4 Q8.8 vectors. Instead of four parallel multipliers I used one signed multiplier time-multiplexed over four cycles, driven by a tiny FSM (IDLE → LOAD → MAC → DONE). That is the area-efficient choice and it is good practice for the streaming version later.

The fixed-point bookkeeping is the part you cannot get sloppy with. A Q8.8 times a Q8.8 is a Q16.16 product, so I accumulate the raw Q16.16 in a wide 40-bit accumulator for headroom, then shift right by 8 (arithmetic >>>, not >>, so the sign bit survives) and saturate to 16 bits exactly once at the end:

Q8.8 * Q8.8  ->  Q16.16 (32b)   // double the fraction bits
acc (40b)    +=  product         // wide, for headroom
s = saturate( acc >>> 8 )         // back to Q8.8, clamp once

Every module gets a valid/ready handshake. That is deliberate — valid/ready is the core of AXI4-Stream, so these blocks will drop straight into a streaming design when I get to the host↔FPGA link.

The testbench drives known vectors through the full handshake and checks three cases — and all three pass:

T1 [1,2,3,4].[1,1,1,1] = 10.0  -> 2560   PASS   // basic
T2 [-1,-2,3,4].[1,1,1,1] = 4.0 -> 1024   PASS   // signed
T3 [100..].[100..] = 40000     -> 32767  PASS   // saturates

Next up is the qkt engine: reuse this one dot4 instance, sequence it over all N×N token pairs with a controller FSM, and apply the 1/√d scale — which is just a right shift here, since my dimensions are powers of two. That one is in progress.

2026-08-01M4 · done

CUDA tiled kernel: load once, reuse many

M4 is the same float32 attention math as the naive kernel — the only thing that changes is where the data lives while I compute. Instead of every thread re-reading Q, K and V straight from global memory, the block stages them into __shared__ memory once, syncs, and then everyone reuses the on-chip copy.

I wanted to actually quantify why that matters, so I counted the global accesses at N = d = d_v = 4 with no caching:

naive:  Q,K,V each read N*N*D = 64  -> 192 reads + 16 writes
distinct input elements          = 3 * 16 = 48
redundancy = 192 / 48            = 4x  (= N)

So the naive kernel re-fetches every key and value row once per query row. Tiling drives those N² terms back toward N: load 48 elements to shared once, reuse them on-chip. At N=4 it is invisible on the clock, but at large N that redundancy is the whole memory-bound problem.

The new hazard is __syncthreads(). It is a block-wide barrier and every thread has to reach every barrier — if you put one after an early return, the threads that returned never arrive and the block deadlocks (technically undefined behavior, which is worse: it might hang, might return garbage, might look fine until it doesn't). The rule I keep repeating to myself: guard the work, not the barrier. Cooperative load inside if(i<N), then an unguarded __syncthreads() that all threads hit, then the guarded compute.

Bugs I hit before it ran (all mine, all caught on the CPU harness):

  • Indexed the shared V tile as sV[c*DV+j] when it should be sV[j*DV+c] — a transpose that silently corrupts the answer. The real one.
  • Scores loop written j < D instead of j < N. Latent, masked by N==D, wrong intent.
  • Wrote the kernel launch with << (bit-shift!) instead of the triple <<<...>>>.
  • Error-check order inverted — copied results back before checking the launch. It has to be launch → getLastError → sync → copy.

Result: max abs err 1.192093e-07, bit-for-bit identical to the naive kernel. Same math, different data path — exactly what I wanted to see.

2026-07-18M3 · done

CUDA naive kernel, and why I went back to float

For the GPU I deliberately dropped the fixed-point work and went back to plain float32. The reason is a rule I keep coming back to: never debug two new things at once. On the GPU I want to isolate did I parallelize correctly? from did I quantize correctly?. So this kernel is float, one thread per output row, and the only question it answers is whether my parallel version matches the golden model.

My dev machine is an M1 Mac with no nvcc, so I write the .cu here and run it on a separate GPU box. To make sure both sides see byte-identical inputs (C++ rand can't reproduce NumPy), I export Q, K, V and the golden O to .npy files and load those in the CUDA host code.

The one real design decision was casting to float32 before saving, rather than exporting float64 and downcasting in CUDA. That keeps a single source of truth — both sides read the identical float32 bytes, so any difference is the kernel's fault and never a silent truncation. It also matches the target hardware and halves the bytes. The known consequence is a hard error floor: the golden is computed in float64 then cast to float32, so even a perfect kernel will differ by float32 rounding. Do not chase it to zero.

Best bug of the milestone was in the .npy loader. The header length is already a byte count, but I wrote fseek(2 * hdr_len, ...) and seeked past the end of the file. The nasty part: seeking past EOF is silently legal and returns 0 — nothing complains until the later fread comes up short, and only its return count tells you. That is exactly why checking fread's return value is load-bearing and not defensive boilerplate. Same silent-failure family as unchecked cudaMemcpy and kernel-launch errors.

Result: max abs err 1.192093e-07 — which is exactly float32 machine epsilon, 2-23, the theoretical floor against an f64-then-f32 golden. You cannot do better, and I hit it.

2026-06-28M2 · done

A fixed-point twin, and the softmax that stopped summing to 1

FPGAs don't hand you floating point, so before touching any HDL I rebuilt the whole model on a Q8.8 integer grid in Python — real numbers scaled by 256 and stored as signed 16-bit integers — and diffed it against the float golden. Same seed, so every difference is genuine quantization error, not input drift.

The single most important rule in the whole file is the grid bookkeeping: a Q8.8 times a Q8.8 is a Q16.16, so after each integer matmul you divide the accumulator by SCALE² = 256² to get back to a real value. And you saturate before storing, or a large value wraps around silently.

Headline number: max abs error 0.00631, mean 0.00205 vs the golden — about 0.6% worst case. That is the error budget I now hold the CUDA and RTL versions to. Being able to quote a concrete number before writing a line of hardware is the entire point of this level.

Two bugs worth remembering. First, I wrote the golden softmax as exp(S - max) and forgot the / sum — the P rows summed to 1.7–2.9 and the output came out about 2× too big. Caught it by just printing P.sum(axis=1). Second, an earlier draft used the raw float V in the P·V step instead of the quantized Vq, so that stage wasn't actually on the grid.

Then the interesting one, which I surfaced on purpose: quantizing a perfectly normalized softmax row breaks its normalization.

Pq row sums (Q8.8): [256, 257, 255, 256]   // should all be 256 = 1.0

Each tiny probability gets rounded onto the lattice and the ±1 errors don't cancel. At N=4 it is only ±1/256; at N=128 you are summing 128 rounding errors and it compounds. The real fix is more fraction bits or an explicit renormalization stage — and now I know I have to budget for that in the RTL. Much cheaper to learn here than on the FPGA.

2026-06-13M1 · done

Starting from a golden model I can trust

Every good hardware project starts with a reference you believe completely, so milestone one is a float64 implementation of single-head scaled dot-product attention in NumPy, at tiny hand-checkable dimensions (N = d = d_v = 4). I built it chunk by chunk: imports and a fixed seed, dimensions, Q/K/V, the scores, a numerically-stable softmax, and the output.

S = Q @ K.T / np.sqrt(d)     # token-by-token scores
P = softmax(S)               # row-max subtract, exp, normalize
O = P @ V                     # weighted blend of the value rows
assert np.allclose(P.sum(axis=1), 1.0)

The assert is the first test in the project: if softmax is on the wrong axis or missing its normalization, the row sums won't be 1 and the script dies. It passed, and by inspection softmax preserves rank (the biggest score in a row becomes the biggest probability) and O leans toward the value row it weights most.

A few things clicked here that pay off at every later level. A matmul eats its shared inner dimension — Q @ K.T contracts the feature dim d to give token×token scores, whereas Q.T @ K would contract tokens and give you something completely different. The 1/√d factor is numerical conditioning so softmax doesn't saturate. And the row-max subtraction before exp is the exact reason a row_max engine will eventually exist in the RTL. keepdims matters too — drop it and the reduction broadcasts against the wrong axis silently.

The real value of this milestone is the discipline: a self-checking float reference with a fixed seed means every lower level has an unambiguous oracle. Any mismatch downstream is a real bug, never input drift.
