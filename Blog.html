Dropping into RTL: a dot-product MAC in SystemVerilog

This is the milestone the whole project was pointing at. I am now building the attention core in synthesizable SystemVerilog, targeting a Xilinx FPGA through Vivado. The build order inside M5 is qkt, then row-max, softmax, PV, and finally the full naive core. I started at the very bottom: the dot-product MAC that lives inside QK⊤.

Step 1: pick the interface and the number format

The unit, dot4, computes sum(a[k]*b[k]) for two length-4 Q8.8 vectors. Two decisions frame everything else. First, the data format is Q8.8: a real number times 256, stored as a signed 16-bit integer. Second, the interface is a valid/ready handshake on both sides, because valid/ready is the core of AXI4-Stream and I want these blocks to drop straight into a streaming design later. The whole vector arrives in one input beat, packed LSB-first.

module dot4 #(
  parameter DW=16, FRAC=8, D=4, ACCW=40
)(
  input  logic clk, rst_n,
  input  logic in_valid,  output logic in_ready,     // input handshake
  input  logic [D*DW-1:0] a_flat, b_flat,            // two packed Q8.8 vectors
  output logic out_valid, input  logic out_ready,    // output handshake
  output logic signed [DW-1:0] s                     // Q8.8 score
);

Step 2: one multiplier, time-multiplexed by an FSM

Instead of four parallel multipliers I use one signed multiplier reused over four cycles. That is the area-efficient choice, and it is driven by a tiny four-state FSM: IDLE waits for an input beat, LOAD latches both vectors, MAC accumulates one product per cycle, and DONE presents the result until the consumer takes it.

typedef enum logic [1:0] { IDLE, LOAD, MAC, DONE } state_t;

always_comb begin
    next_state = curr_state;
    case (curr_state)
        IDLE: if (in_valid && in_ready)   next_state = LOAD;
        LOAD:                            next_state = MAC;
        MAC:  if (idx_counter == D-1)    next_state = DONE;
        DONE: if (out_valid && out_ready) next_state = IDLE;
    endcase
end

Step 3: the datapath, and the fixed-point bookkeeping

On LOAD I slice each 16-bit element out of the flat bus with a part-select. The [i*DW +: DW] syntax means "pick DW bits starting at bit i*DW", which is exactly how you unpack a packed vector:

for (int i = 0; i < D; i++) begin
    a_reg[i] <= a_flat[i*DW +: DW];   // DW bits starting at i*DW
    b_reg[i] <= b_flat[i*DW +: DW];
end

Then on each MAC cycle I add one product into a wide accumulator. This is the part you cannot get sloppy with: a Q8.8 times a Q8.8 is a Q16.16 product, so I keep the raw Q16.16 in a 40-bit accumulator for headroom rather than truncating mid-sum.

end else if (curr_state == MAC) begin
    acc <= acc + (a_reg[idx_counter] * b_reg[idx_counter]); // Q16.16 into wide acc
    idx_counter <= idx_counter + 1;
end

Only at the very end do I shift back down to Q8.8 and saturate, exactly once. The shift is an arithmetic >>>, not a logical >>, so the sign bit survives on negative results, and the clamp keeps an overflow from wrapping silently:

assign shifted = acc >>> FRAC;         // Q16.16 -> Q8.8, keep the sign bit

always_comb begin
    if      (shifted > sMAX) s = sMAX;  // clamp high
    else if (shifted < sMIN) s = sMIN;  // clamp low
    else    s = shifted[DW-1:0];        // in range
end

Step 4: drive the handshake from the state

The handshake outputs are just decodes of the FSM state, which keeps them glitch-free and easy to reason about: ready to accept only in IDLE, result valid only in DONE.

assign in_ready  = (curr_state == IDLE);
assign out_valid = (curr_state == DONE);

Step 5: prove it in simulation

The testbench drives known vectors through the full handshake (present a, b and in_valid, wait for the accept beat, drop in_valid, wait for out_valid, sample s) and checks three cases. All three pass:

T1 [1,2,3,4].[1,1,1,1] = 10.0  -> 2560   PASS   // basic
T2 [-1,-2,3,4].[1,1,1,1] = 4.0 -> 1024   PASS   // signed
T3 [100..].[100..] = 40000     -> 32767  PASS   // saturates

What is next: the QK⊤ engine

The engine above dot4 reuses that single instance and sequences it over all N×N token pairs with a controller FSM that drives dot4's own valid/ready lines: ISSUE presents q_mem[i] and k_mem[j], WAIT holds until dot4 raises out_valid, then it captures the score and advances i, j. The 1/√d scale is a plain right shift here, because my dimensions are powers of two. That controller is what I am wiring up now.

// S[i][j] = (Q_row_i . K_row_j) / sqrt(d)   for all i, j
// reuse ONE dot4, sequenced over N*N pairs by a controller FSM:
//   IDLE -> ISSUE (drive dot4 in_valid) -> WAIT (dot4 out_valid) -> ISSUE/DONE
// scale by 1/sqrt(d) = right shift SQRTD_SH   (dims are powers of 2)

CUDA tiled kernel: load once, reuse many

M4 is the same float32 attention math as the naive kernel. The only thing that changes is where the data lives while I compute. Instead of every thread re-reading Q, K and V straight from global memory, the block stages them into on-chip shared memory once, syncs, and then everyone reuses that copy.

Why this matters: count the reads

I wanted to actually quantify the win at N = d = d_v = 4 with no caching. In the naive kernel every one of the N threads reads all of Q, K and V, so each of those three tensors gets read N×N×D = 64 times, for 192 reads total. But there are only 3×16 = 48 distinct input elements. That is a 4× redundancy, which is exactly N. Tiling drives those N² terms back toward N: load the 48 elements to shared once, reuse on-chip. This is why the memory hierarchy matters, roughly registers at ~1 cycle, shared at ~20-30, global at ~400-600.

naive:  Q,K,V each read N*N*D = 64  -> 192 reads + 16 writes
distinct input elements          = 3 * 16 = 48
redundancy = 192 / 48            = 4x  (= N)

Step 1: declare the shared tiles and load them cooperatively

A __shared__ array is one copy per block, visible to every thread in it, alive only while the block runs. The cooperative load has thread i copy row i of each tensor, which is also nicely coalesced because a row is contiguous:

__shared__ float sQ[N*D];       // one copy per block, all threads see it
__shared__ float sK[N*D];
__shared__ float sV[N*DV];

int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < N) {                     // COOPERATIVE LOAD: thread i loads row i
    for (int k = 0; k < D;  k++) sQ[i*D + k]  = Q[i*D + k];
    for (int k = 0; k < D;  k++) sK[i*D + k]  = K[i*D + k];
    for (int c = 0; c < DV; c++) sV[i*DV + c] = V[i*DV + c];
}

Step 2: the barrier, and where to put it

This is the new hazard. __syncthreads() is a block-wide barrier, and every thread has to reach every barrier. If you put one after an early return, the threads that returned never arrive and the block deadlocks (technically undefined behavior, which is worse: it might hang, might return garbage, might look fine until it doesn't). The rule I keep repeating to myself is guard the work, not the barrier: the load is guarded, the sync is not, then the compute is guarded again.

__syncthreads();                // ALL threads reach this - never return before it

if (i < N) {                     // guard the WORK, not the barrier
    // same math as M3, but reading from sQ / sK / sV instead of global
    // dot -> row-max -> exp/sum -> normalize -> PV
    O[i*DV + c] = val;
}

One design note: I deliberately do not stage O in shared. It is written exactly once per element by its owner thread with zero reuse, so it goes straight to global. Shared memory is for reused inputs, not write-once outputs.

The bugs I hit (all caught before the GPU)

  • Indexed the shared V tile as sV[c*DV+j] when it should be sV[j*DV+c]. A transpose that silently corrupts the answer. The real one.
  • Scores loop written j < D instead of j < N. Latent, masked by N==D, wrong intent.
  • Wrote the launch with << (a bit-shift) instead of the triple <<<...>>>.
  • Error-check order inverted: copied results back before checking the launch. It has to be launch, getLastError, sync, then copy.

Result: max abs err 1.192093e-07, bit-for-bit identical to the naive kernel. Same math, different data path, exactly what I wanted to see.

CUDA naive kernel, and why I went back to float

For the GPU I deliberately dropped the fixed-point work and went back to plain float32. The reason is a rule I keep coming back to: never debug two new things at once. On the GPU I want to isolate did I parallelize correctly? from did I quantize correctly?. So this kernel is float, one thread per output row, and the only question it answers is whether my parallel version matches the golden model.

Step 1: a data bridge, byte-for-byte

My dev machine is an M1 Mac with no nvcc, so I write the .cu here and run it on a separate GPU box. C++ rand cannot reproduce NumPy, so I export Q, K, V and the golden O to .npy and load those. I cast to float32 before saving rather than exporting float64 and downcasting in CUDA, so both sides read the identical bytes. Any difference is then the kernel's fault, never a silent truncation. The known cost is a hard error floor, since the golden is float64 cast to float32.

Step 2: parse the .npy header, then read the floats

A .npy file is a small magic string, a version, a 2-byte header length, an ASCII dict header, then the raw row-major data. I already know the shape, so I skip the header and read the payload. The bug here taught me the most: the header length is already a byte count, but I first wrote fseek(f, 2*hdr_len, ...) and seeked past the end of the file. Seeking past EOF is silently legal and returns 0; nothing complains until the later fread comes up short. That is why checking fread's return is load-bearing, not defensive boilerplate:

fseek(f, 8, SEEK_SET);                    // skip magic (6B) + version (2B)
uint16_t hdr_len;
fread(&hdr_len, sizeof(uint16_t), 1, f);  // header length, in bytes
fseek(f, hdr_len, SEEK_CUR);              // NOT 2*hdr_len - already a byte count
size_t got = fread(data, sizeof(float), rows*cols, f);
if ((size_t)(rows*cols) != got) { /* fread's return is the only witness */ }

Step 3: one thread computes one output row

The kernel maps thread i to output row i, guards the over-provisioned threads, and then walks the attention math straight through: dot products for the scores, subtract the row max for stability, exp and sum, normalize, then the PV blend.

__global__ void attention_kernel(const float* Q, const float* K,
                                  const float* V, float* O) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= N) return;                     // one thread per output row
    float s[N];

    for (int j = 0; j < N; j++) {           // scores: dot(Q[i],K[j]) / sqrt(D)
        float dot = 0.0f;
        for (int k = 0; k < D; k++) dot += Q[i*D + k] * K[j*D + k];
        s[j] = dot / sqrtf((float) D);
    }
    float m = s[0];                         // row max (stable softmax)
    for (int j = 1; j < N; j++) if (s[j] > m) m = s[j];

    float denom = 0.0f;                     // exp + sum
    for (int j = 0; j < N; j++) { s[j] = expf(s[j] - m); denom += s[j]; }
    for (int j = 0; j < N; j++) s[j] /= denom;        // normalize

    for (int c = 0; c < DV; c++) {          // PV
        float acc = 0.0f;
        for (int j = 0; j < N; j++) acc += s[j] * V[j*DV + c];
        O[i*DV + c] = acc;
    }
}

Step 4: the host flow, in strict order

Host side is load, allocate on the device, copy in, launch, then check the launch before touching the results. The launch is async and returns void, so you catch config errors with cudaGetLastError() and runtime errors with cudaDeviceSynchronize(), which also acts as the barrier before the copy back:

attention_kernel<<<numBlocks, threadsPerBlock>>>(dQ, dK, dV, dO);
CUDA_CHECK(cudaGetLastError());       // launch-config error
CUDA_CHECK(cudaDeviceSynchronize());  // runtime error + barrier before D2H
CUDA_CHECK(cudaMemcpy(hO, dO, N*DV*sizeof(float), cudaMemcpyDeviceToHost));

Result: max abs err 1.192093e-07, which is exactly float32 machine epsilon, 2-23, the theoretical floor against an f64-then-f32 golden. You cannot do better, and I hit it.

A fixed-point twin, and the softmax that stopped summing to 1

FPGAs do not hand you floating point, so before touching any HDL I rebuilt the whole model on a Q8.8 integer grid in Python and diffed it against the float golden. Same seed, so every difference is genuine quantization error, not input drift.

Step 1: the quantize / dequantize / saturate helpers

Q8.8 means a real number times SCALE = 28 = 256, rounded to an integer, stored in 16 bits. The one rule that matters most is saturate before storing: quantize clamps internally so a caller can never forget and let a large value wrap around.

FRAC = 8
SCALE = 2 ** FRAC              # 256
BITS = 16
INT_MIN, INT_MAX = -2**(BITS-1), 2**(BITS-1) - 1   # -32768 .. 32767

def saturate(q):
    return np.clip(q, INT_MIN, INT_MAX)            # clamp before storing

def quantize(x):
    return saturate(np.round(x * SCALE).astype(int))

def dequantize(q):
    return q / SCALE

Step 2: do QK⊤ and PV on the integer grid

Here is the bookkeeping that the whole file lives or dies on: multiplying two Q8.8 numbers doubles the fraction bits to Q16.16, so after each integer matmul I divide the accumulator by SCALE² to get back to a real value. QK⊤ needs the transpose to contract the feature dim; PV does not, because its shared keys axis is already aligned.

Qq, Kq = quantize(Q), quantize(K)      # Q8.8 integers
S_raw   = Qq @ Kq.T                    # integer matmul -> Q16.16
S_fixed = (S_raw / (SCALE * SCALE)) / np.sqrt(d)   # /SCALE^2, then /sqrt(d)

# ... softmax (see below) produces P_fixed ...

Vq, Pq = quantize(V), quantize(P_fixed)
O_raw   = Pq @ Vq                      # integer matmul -> Q16.16
O       = O_raw / (SCALE * SCALE)      # dequantize back to real

Step 3: keep softmax's exp in float (for now)

Only QK⊤ and PV are truly on the grid in this milestone. The softmax exp stays in float, because a proper fixed-point exp is a lookup table that mirrors the RTL exp stage, and that is a later pass. Scoping it this way keeps one thing at a time on the grid:

m = np.max(S_fixed, axis=1, keepdims=True)
e = np.exp(S_fixed - m)                        # exp still float here
P_fixed = e / np.sum(e, axis=1, keepdims=True)

The result, and the bug I surfaced on purpose

Headline: max abs error 0.00631, mean 0.00205 versus the golden, about 0.6% worst case. That is the error budget I now hold the CUDA and RTL versions to. Being able to quote a concrete number before writing a line of hardware is the entire point of this level.

One bug worth remembering: I first wrote the golden softmax as exp(S - max) and forgot the / sum, so the rows summed to 1.7 to 2.9 and the output came out about 2× too big. I caught it by just printing P.sum(axis=1). Then the interesting one, surfaced on purpose: quantizing a perfectly normalized softmax row breaks its normalization.

Pq row sums (Q8.8): [256, 257, 255, 256]   // should all be 256 = 1.0

Each tiny probability gets rounded onto the lattice and the plus-or-minus-1 errors do not cancel. At N=4 it is only about 1/256; at N=128 you are summing 128 rounding errors and it compounds. The real fix is more fraction bits or an explicit renormalization stage, and now I know I have to budget for that in the RTL. Much cheaper to learn here than on the FPGA.

Starting from a golden model I can trust

Every good hardware project starts with a reference you believe completely, so milestone one is a float64 implementation of single-head scaled dot-product attention in NumPy, at tiny hand-checkable dimensions (N = d = d_v = 4). I built it chunk by chunk, and each chunk exists for a reason.

Step 1: seed, dimensions, and the inputs

The fixed seed is the contract that makes every later cross-level diff meaningful: identical Q, K, V on every run and in every downstream version. The dimensions are deliberately tiny so I can check the numbers by hand.

import numpy as np
np.random.seed(0)                 # fixed inputs = unambiguous oracle

N, d, d_v = 4, 4, 4
Q = np.random.randn(N, d)         # queries
K = np.random.randn(N, d)         # keys
V = np.random.randn(N, d_v)       # values

Step 2: scores, with the 1/√d scale

A matmul eats its shared inner dimension. Q @ K.T contracts the feature dim d to give a token-by-token score matrix; Q.T @ K would contract tokens instead and give you something completely different. The 1/√d factor is numerical conditioning so the softmax does not saturate.

S = Q @ K.T / np.sqrt(d)          # (N,d).(d,N) -> (N,N), contracts d

Step 3: a numerically stable softmax

Subtracting the row max before exp is mathematically identical to plain softmax but prevents overflow. This is the exact reason a row_max engine will eventually exist in the RTL. And keepdims=True matters: it keeps the reductions as (N,1) so they broadcast down the rows. Drop it and the reduction broadcasts against the wrong axis, silently wrong with no crash.

max_ = np.max(S, axis=1, keepdims=True)    # (N,1)
exp_ = np.exp(S - max_)                     # (N,N), stable
sum_ = np.sum(exp_, axis=1, keepdims=True)  # (N,1)
P = exp_ / sum_                             # rows now sum to 1

Step 4: the output, and the first test in the project

PV needs no transpose (its shared keys axis is already aligned), so O is just the weighted blend of the value rows. The assert is the first test in the whole project: if softmax landed on the wrong axis or lost its normalization, the row sums are not 1 and the script dies on the spot.

O = P @ V
assert np.allclose(P.sum(axis=1), 1.0)     # softmax rows must sum to 1

It passed, and by inspection softmax preserves rank (the biggest score in a row becomes the biggest probability) and O leans toward the value row it weights most. The real value of this milestone is the discipline: a self-checking float reference with a fixed seed means every lower level has an unambiguous oracle, so any mismatch downstream is a real bug, never input drift.
